## 1. 지금 무엇이 문제인가

새로 만들자는 판단의 근거를 먼저 정리합니다. 감이 아니라 지금 코드에서 측정된 것들입니다.

**① 한 파일에 전부 들어 있다**
`admin.js` 가 5,743줄, 전역 함수 84개입니다. 여기에 근태·게시판·재고까지 얹으면 한 줄 고칠 때마다 무엇이 깨질지 알 수 없게 됩니다.

**② 팀 업무가 한 화면에 섞여 있다**
말씀하신 "하나 확인하려면 검수·매입완료를 다 봐야 한다"가 정확히 이 문제입니다. 배송 담당자가 오늘 수거 나갈 건만 보고 싶어도 검수 대기, 입금 완료가 같이 보입니다. 사람이 눈으로 걸러내는 비용이 매일 발생합니다.

**③ 고객 사이트와 같은 곳에 배포된다**
관리자 파일을 고치고 배포하면 고객 사이트도 같이 나갑니다. 실수 하나가 매출에 직접 닿습니다.

**④ 화면 코드가 데이터베이스를 직접 호출한다**
같은 조회가 파일 곳곳에 복사돼 있습니다. 지난번 관리자페이지가 느려졌던 원인도 여기였습니다 — 정렬(`orderBy`) 없는 조회가 건당 13배 느리다는 걸 실측으로 확인했는데, 그런 조회가 어디에 몇 개 있는지 코드만 봐서는 알 수 없는 구조였습니다.

**⑤ 권한이 하나뿐이다**
`isAdmin()` 하나로 전부 통과합니다. 직원 누구나 매입가를 바꾸고 입금 처리를 할 수 있습니다. 15명 규모에서는 위험합니다.

## 2. 전체 구조

```
Firebase 프로젝트 (rejeuphone) — 그대로 사용
│
├─ Firestore  ← 데이터는 한 곳. 고객 사이트와 직원 앱이 같은 걸 본다
│    quotes / users / products / reviews / chats /
│    blacklist / exchange_applications
│    + attendance (근태)  posts (게시판)  staff (직원)  ← 새로 추가
│
├─ Cloud Functions  ← 서버에서만 해야 하는 일
│    알림톡 발송 · 시트 연동 · 출퇴근 기록 · 통계 집계 · 권한 부여
│
└─ Hosting  ← 여기만 둘로 나눈다
     ├─ sharaphone.com        고객 사이트 (지금 그대로)
     └─ staff.sharaphone.com  직원 앱 (새로 만듦)
```

**핵심은 "데이터는 합치고, 배포는 나눈다"입니다.**

데이터를 나누면 신청 정보를 두 곳에 동기화해야 해서 지옥이 됩니다. 반대로 배포를 합쳐두면 지금처럼 관리자 수정이 고객 사이트를 건드립니다. Firebase Hosting은 한 프로젝트에 여러 사이트를 둘 수 있어서, 이 조합이 가능합니다.

```bash
# 직원 앱만 배포 — 고객 사이트는 손대지 않음
firebase deploy --only hosting:staff

# 고객 사이트만 배포
firebase deploy --only hosting:main
```

## 3. 기술 스택

| 무엇 | 선택 | 이유 |
|---|---|---|
| 화면 | **React 18** | 자료와 예제가 압도적으로 많음. AI 지원도 가장 정확함 |
| 언어 | **TypeScript** | 아래 별도 설명 |
| 빌드 | **Vite** | 설정이 단순하고 빠름. 결과물이 정적 파일이라 Firebase Hosting에 그대로 올라감 |
| 화면 이동 | React Router | 표준 |
| 데이터 관리 | **TanStack Query** | 조회 결과 캐싱·자동 갱신. 관리자페이지 속도 문제의 구조적 해법 |
| 표 | TanStack Table | 정렬·필터·가상 스크롤. 신청 목록에 필수 |
| 디자인 | Tailwind + shadcn/ui | 컴포넌트를 직접 만들 필요가 없음 |
| 데이터베이스 | Firebase SDK v10 | 지금 쓰는 것 그대로 |

### TypeScript를 쓰는 이유

지금 `quotes` 문서는 필드가 제각각입니다. 접수 시각이 어떤 문서엔 `firebaseTimestamp`, 어떤 문서엔 `submittedAt` 으로 들어 있고, `status` 는 `"입금완료"` 같은 한글 문자열이라 오타 하나면 조용히 안 걸립니다. 실제로 이것 때문에 여러 번 고쳤습니다.

TypeScript를 쓰면 이런 걸 **코드를 실행하기 전에** 잡아냅니다.

```typescript
// types/quote.ts — 신청건이 가질 수 있는 모양을 한 곳에 못박는다
export type QuoteStatus =
  | '신청접수' | 'receipt' | '입고완료' | '검수중'
  | '견적안내' | '입금완료' | '반송접수' | '취소';

export type DeliveryMethod = 'courier' | 'cvs' | 'pending';

export interface Quote {
  id: string;
  customerName: string;
  customerPhone: string;
  brand: string;
  model: string;
  status: QuoteStatus;          // 오타 내면 즉시 에러
  deliveryMethod: DeliveryMethod;
  submittedAt: Date;            // 변환기가 통일해서 넣어줌
  finalPrice: number | null;
  isDeleted?: boolean;
}
```

`status: '입금 완료'` 처럼 띄어쓰기 하나만 틀려도 저장 전에 빨간 줄이 그어집니다. 지금 구조에서는 배포하고 며칠 뒤에 "왜 이 건이 목록에 안 뜨지"로 발견됩니다.

### 대안 검토

**Next.js** — 사내 도구에는 과합니다. 검색 노출이 필요 없고, 서버 렌더링도 필요 없습니다. 배포도 더 복잡해집니다.

**지금처럼 순수 JS 유지** — 파일이 30개를 넘어가면 감당이 안 됩니다. 이미 그 한계에 와 있습니다.

**노코드 도구 (Retool 등)** — 초기엔 빠르지만 알림톡 발송, 굿스플로 연동 같은 커스텀 로직이 많아 결국 막힙니다.

## 4. 팀 구분 설계 ⭐

이 프로그램의 핵심입니다. **팀별로 화면을 나누는 게 아니라, 일의 흐름을 나누고 각 팀에게 자기 구간만 보여줍니다.**

### 4.1 신청건이 지나가는 길

```
 접수 ──▶ 수거/발송 ──▶ 입고 ──▶ 검수 ──▶ 견적안내 ──▶ 고객동의 ──▶ 입금 ──▶ 완료
                                                        │
                                                        └──▶ 반송
 └──────── 배송·CS팀 ────────┘└──── 검수팀 ────┘└─ 관리자 ─┘
                                    └── 배송·CS팀 (반송) ──┘
```

### 4.2 팀별 담당 구간

| 팀 | 담당하는 일 | 주로 보는 상태 |
|---|---|---|
| **배송·CS팀** | 수거 배차, 송장 관리, 미집하 추적, 고객 문의 응대, 반송 처리, 취소 처리 | 신청접수 · 수거대기 · 미집하 · 반송접수 |
| **검수팀** | 입고 확인, 기기 검수, 등급 확정, 견적 안내, 재고 등록 | 입고완료 · 검수중 · 견적안내 · 고객응답대기 |
| **개발팀** | 시스템 설정, 가격표 관리, 데이터 점검 도구, 배포 | 전체 (읽기) + 설정 |
| **관리자/대표** | 최종 매입가 확정, 입금 처리, 근태 승인, 통계 | 전체 |

### 4.3 화면 구조

각 팀은 로그인하면 **"내가 지금 처리해야 할 것"** 만 봅니다.

```
┌─ 배송·CS팀 홈 ───────────────────────────────┐
│                                              │
│  오늘 수거 예정        12건   [처리하기]     │
│  송장 미입력            4건   [처리하기]     │
│  미집하 3일 경과        2건   ⚠ [확인]       │
│  반송 대기              1건   [처리하기]     │
│  고객 문의 미답변       3건   [처리하기]     │
│                                              │
└──────────────────────────────────────────────┘

┌─ 검수팀 홈 ──────────────────────────────────┐
│                                              │
│  입고 확인 대기         8건   [처리하기]     │
│  검수 대기             15건   [처리하기]     │
│  견적 안내 대기         5건   [처리하기]     │
│  고객 응답 대기 (3일↑)  2건   ⚠ [확인]       │
│                                              │
└──────────────────────────────────────────────┘
```

**신청건 상세 화면은 하나만 만듭니다.** 어느 팀이 열든 같은 화면이 뜨지만, 자기 담당 구간만 수정할 수 있습니다.

| 상세 화면 영역 | 배송·CS | 검수 | 개발 | 관리자 |
|---|:---:|:---:|:---:|:---:|
| 고객 정보 | 보기+수정 | 보기 | 보기 | 보기+수정 |
| 배송/송장 | **수정** | 보기 | 보기 | 수정 |
| 검수 결과·등급 | 보기 | **수정** | 보기 | 수정 |
| 최종 매입가 | 보기 | 제안만 | 보기 | **확정** |
| 입금 처리 | ✕ | ✕ | ✕ | **가능** |
| 삭제 | ✕ | ✕ | ✕ | 가능 |

검수팀은 금액을 **제안**만 하고, 확정은 관리자가 합니다. 지금은 누구나 확정·입금까지 가능한 상태라 이 분리 하나만으로도 사고 위험이 크게 줍니다.

### 4.4 공용 기능

팀과 무관하게 모두가 씁니다.

- 출퇴근 체크 / 내 근무시간
- 공지사항 / 게시판
- 내 정보 (연락처, 계좌, 비밀번호)
- 전체 검색 (고객명·연락처로 신청건 찾기)

### 4.5 직원 정보 저장 형태

```
staff/{uid}
{
  name: "홍길동",
  email: "hong@sharaphone.com",
  team: "delivery",              // delivery | inspection | dev | admin
  role: "member",                // member | lead | manager | owner
  phone: "010-0000-0000",
  joinedAt: Timestamp,
  active: true                   // 퇴사 시 false (기록은 남김)
}
```

권한은 Firestore 문서만 믿으면 안 됩니다. 로그인 시 Cloud Functions가 **커스텀 클레임**으로 심어주고, Firestore 보안 규칙이 그 클레임을 검사합니다. 문서만 보고 판단하면 클라이언트에서 우회할 수 있습니다.

```javascript
// firestore.rules
function team()      { return request.auth.token.team; }
function isManager() { return request.auth.token.role in ['manager','owner']; }

match /quotes/{id} {
  allow read: if request.auth != null;

  // 배송 담당 필드는 배송팀과 관리자만
  allow update: if team() == 'delivery' &&
    request.resource.data.diff(resource.data).affectedKeys()
      .hasOnly(['deliveryMethod','trackingNumber','pickupDate','status','memo']);

  // 금액 확정·입금은 관리자만
  allow update: if isManager();
}
```

### 변환기가 하는 일

```typescript
// repositories/converters.ts
// 지금 문서마다 제각각인 필드를 여기서 한 번에 통일한다.
// 화면 코드는 항상 submittedAt(Date) 하나만 보면 된다.
export const toQuote = (id: string, d: DocumentData): Quote => ({
  id,
  customerName: d.customerName ?? '',
  customerPhone: normalizePhone(d.customerPhone),
  status: d.status ?? '신청접수',
  submittedAt: toDate(d.submittedAt ?? d.firebaseTimestamp),  // ← 흡수
  finalPrice: typeof d.finalPrice === 'number' ? d.finalPrice : null,
  ...
});
```

지금은 이 분기가 `admin.js` 안에 `_toDateForList()` 같은 이름으로 여러 군데 흩어져 있습니다. 한 곳으로 모으면 새 필드가 생겨도 고칠 데가 한 군데입니다.

## 6. 기능별 설계

### 6.1 출퇴근 (공용)

**월 단위 문서 한 개**로 저장합니다.

```
attendance/{2026-08}_{uid}
{
  uid, year: 2026, month: 8,
  days: {
    "01": { in: Timestamp, out: Timestamp, workMin: 480, note: "" },
    "02": { in: Timestamp, out: Timestamp, workMin: 505, note: "" }
  },
  totalMin: 9840,
  edits: [ { by, at, day, before, after, reason } ]   // 수정 이력
}
```

**왜 월 단위인가** — 한 달 근무표를 보는 데 읽기 1번이면 됩니다. 날짜별 문서로 나누면 31번을 읽습니다. 15명 전체 월간 조회가 **465회 → 15회**로 줄어듭니다. 관리자페이지가 느렸던 것과 같은 종류의 문제를 처음부터 피하는 설계입니다.

**시각은 반드시 서버에서 찍습니다.** 브라우저 시각을 쓰면 폰 시계를 바꿔 조작할 수 있습니다.

```javascript
// functions/attendance.js
exports.punch = onCall(async (req) => {
  const uid = req.auth.uid;
  const now = admin.firestore.Timestamp.now();   // ★ 서버 시각
  // ... days[오늘] 에 in 또는 out 기록
});
```

**수정 이력을 남깁니다.** 근로기준법상 근로시간 기록은 3년 보관 의무가 있습니다. 관리자가 근태를 고쳤다면 누가·언제·왜 고쳤는지 남아 있어야 나중에 분쟁이 없습니다.

**화면**

- 휴대폰: 큰 버튼 하나 (`출근` / `퇴근`) + 오늘 근무시간
- PC: 같은 버튼 + 이번 달 달력 + 누적 시간
- 관리자: 팀별 월간 표, 엑셀 내보내기

### 6.2 공지사항 · 게시판 (공용)

```
posts/{postId}
{
  title, body, authorUid, authorName,
  category: 'notice' | 'free' | 'delivery' | 'inspection' | 'dev',
  pinned: false,
  mustRead: false,          // 필독 공지
  readBy: [uid, uid, ...],  // 누가 읽었는지
  createdAt, updatedAt
}
posts/{postId}/comments/{commentId}
```

필독 공지는 안 읽은 사람에게 홈 상단에 계속 뜹니다. 카테고리로 팀별 게시판이 자연스럽게 나뉩니다.

### 6.3 신청관리 (배송·CS팀 + 검수팀)

기존 관리자페이지에서 옮겨옵니다. 달라지는 건 **하나의 큰 표가 아니라 팀별 큐**라는 점입니다.

- 목록: 커서 페이지네이션 (한 번에 50건)
- 검색: 이름·연락처·모델
- 상세: 한 화면, 팀별로 편집 가능 영역만 열림
- 처리 이력: 누가 언제 무엇을 바꿨는지 `quotes/{id}/history` 에 기록

### 6.4 배송관리 (배송·CS팀)

- 오늘 수거 예정 목록 → 굿스플로 배차
- 송장 미입력 건 추적
- 미집하 경과일 자동 표시 (3일 이상 경고)
- 반송 처리
- 착불 발송 건 도착 확인

### 6.5 재고관리 (검수팀)

지금 없는 기능이라 새로 설계합니다.

```
inventory/{itemId}
{
  quoteId,                     // 어느 신청건에서 왔는지
  imei, brand, model, storage, color,
  grade: 'S'|'A'|'B'|'C'|'D',
  purchasePrice,               // 매입가
  location: '검수실'|'보관함A'|'출고대기',
  status: 'inspecting'|'stocked'|'sold'|'returned',
  soldTo, soldPrice, soldAt,
  createdAt
}
```

검수 완료 → 재고 자동 등록 → 판매 시 출고. 기기 하나가 매입부터 판매까지 이어지므로 마진을 실제로 계산할 수 있습니다. 지금은 이 연결이 없어서 기기별 수익을 못 봅니다.

### 6.6 메신저

**직접 만들지 않습니다.** 읽음 표시, 알림, 파일 전송, 검색까지 제대로 하려면 그것만으로 프로젝트 하나입니다. 15명 규모에서 자체 개발할 이유가 없습니다.

대신 **업무 알림을 슬랙/카카오워크로 쏘는 연동**을 붙입니다. 이게 실제로 필요한 부분입니다.

```
신규 신청 접수      → #배송cs 채널
미집하 3일 경과     → #배송cs 채널  ⚠
검수 대기 20건 초과 → #검수 채널
고객 반송 요청      → #배송cs 채널
서버 오류           → #개발 채널
```

지금 텔레그램으로 일부 알림을 보내고 있는데, 그걸 팀별 채널로 정리하는 셈입니다.

## 7. 성능 규칙 — 지난 경험을 규칙으로

관리자페이지가 느려졌던 원인을 실측으로 찾았습니다. 그때 배운 걸 처음부터 규칙으로 박아둡니다.

| 규칙 | 근거 |
|---|---|
| 목록 조회는 **반드시** `orderBy` + `limit` | 정렬 없는 조회가 건당 13배 느림 (554건 6,742ms vs 정렬 300건 272ms) |
| 건수는 `getCountFromServer` | 문서를 다 읽지 않음 (95ms) |
| 여러 문서를 훑는 통계는 **요약 문서**로 | `stats/returning_customers` 방식. Cloud Functions가 갱신 |
| 전체 조회가 필요하면 `documentId()` 커서 페이지네이션 | 15,935ms → 963ms 개선 확인됨 |
| 자주 안 바뀌는 데이터는 TanStack Query `staleTime` 으로 재조회 억제 | 화면 이동마다 다시 읽는 낭비 제거 |

## 8. 개발 순서

**근태부터 시작하는 걸 권합니다.**

기존 시스템과 겹치지 않아 망가뜨릴 게 없고, 직원들이 매일 쓰니 피드백이 빨리 옵니다. 신청관리부터 하면 검증 부담이 크고, 하나 놓치면 바로 업무가 멈춥니다.

| 단계 | 내용 | 예상 | 위험 |
|---|---|---|---|
| **0** | 프로젝트 뼈대, 로그인, 권한, 팀별 홈 껍데기 | 1~2주 | 없음 |
| **1** | **출퇴근 + 내 근무시간 + 관리자 월간표** | 1주 | 없음 |
| **2** | 공지사항 · 게시판 | 1주 | 없음 |
| **3** | 신청관리 이전 (목록·상세·상태변경·알림톡) | 2~3주 | 중간 — 기존과 병행하며 대조 |
| **4** | 배송관리 이전 (굿스플로·미집하) | 1~2주 | 중간 |
| **5** | 재고관리 (신규) | 2주 | 낮음 |
| **6** | 슬랙/카카오워크 알림 연동 | 3일 | 없음 |
| **7** | 기존 관리자페이지 폐기 | — | — |

3단계부터는 **기존 관리자페이지를 켜둔 채로** 새 화면과 숫자를 대조하면서 넘어갑니다. 같은 Firestore를 보므로 데이터는 항상 같습니다. 며칠 양쪽을 같이 보다가 새 쪽이 맞다는 확신이 서면 옮깁니다.

## 9. 개발 도구 — Claude Code를 권합니다

**예, 이 프로젝트는 Claude Code가 맞습니다.**

| | 지금 방식 (Cowork) | Claude Code |
|---|---|---|
| 잘 맞는 일 | 파일 몇 개 고치기, 진단 도구 만들기, 배포 명령 안내 | 파일 수십~수백 개짜리 프로젝트를 계속 만들고 고치기 |
| 빌드·실행 | 안 됨 | `npm run dev` 로 바로 확인 |
| 에러 확인 | 배포해야 앎 | 타입 오류·빌드 실패를 즉시 잡음 |
| git | 제한적 | 브랜치·커밋 관리 |

지금까지처럼 파일 몇 개 고치는 일은 여기서도 충분했습니다. 하지만 이 프로젝트는 파일이 50~100개가 됩니다. TypeScript는 저장할 때마다 타입 검사를 돌려야 이득이 나오는데, 그게 Claude Code에서 됩니다.

**현실적인 조합을 제안합니다.**

- **뼈대 세우기** — 여기서 진행. 폴더 구조, 타입 정의, Firestore 규칙, 리포지토리 기본형까지 만들어 드립니다. 이게 제일 중요하고 한 번만 하면 되는 일입니다.
- **반복 개발** — Claude Code. 화면 하나씩 붙여가는 작업.
- **배포** — 지금처럼 Gemini로 하셔도 되고, Claude Code에서 바로 하셔도 됩니다.

Claude Code는 터미널 도구라 처음엔 낯설 수 있습니다. 설치와 첫 실행까지는 제가 안내해 드릴 수 있습니다.

## 10. 솔직하게 말씀드릴 부분

**① 범위가 큽니다**
0~7단계 전부면 **3~4개월** 규모입니다. 본업을 하면서라면 더 걸립니다. 그래서 단계를 나눴습니다. 1~2단계(근태·게시판)만 해도 한 달이면 쓸 수 있고, 거기서 멈춰도 손해가 아닙니다.

**② 근태만 필요하면 기성 서비스가 쌉니다**
시프티, 알밤 같은 서비스가 15명 기준 월 3~5만원입니다. 자체 개발이 의미 있는 건 **근태가 신청·배송·재고와 한 프로그램 안에 있을 때**입니다. 직원이 출근 버튼 누른 화면에서 바로 오늘 검수할 목록이 보이는 것, 그게 목적이라면 자체 개발이 맞습니다. 근태만 따로 필요한 거라면 기성품이 낫습니다.

**③ 재고관리는 실제 업무 흐름을 더 들어야 합니다**
지금 검수 후 기기를 어떻게 보관하고 어디로 파는지(도매? 개별 판매?)에 따라 설계가 꽤 달라집니다. 5단계에 가서 다시 이야기하는 게 좋겠습니다.

**④ 기존 관리자페이지는 당장 버리지 마세요**
새 앱이 안정될 때까지 켜두는 게 맞습니다. 병행 기간의 유일한 비용은 "두 곳을 다 봐야 한다"인데, 데이터가 같으니 틀어질 위험은 없습니다.

## 12. 개발 도구 조합 — Claude Code + Antigravity

두 도구를 다 쓸 수 있다면, 하나로 몰지 말고 **역할을 나누는 편이 낫습니다.**

### 각자 잘하는 것

| | Claude Code | Antigravity |
|---|---|---|
| 성격 | 터미널 기반. 규칙 문서(`CLAUDE.md`)를 지키며 일관되게 작업 | 에이전트 우선 IDE. 계획·실행·검증까지 스스로 |
| 강한 지점 | 구조 유지, 대규모 리팩터링, 긴 맥락 | **Firebase 통합**, 브라우저로 결과 검증, 병렬 작업, 예약 실행 |
| 이 프로젝트에서 | 기능 개발 본체 | 인프라 설정 · 배포 · 검증 |

### 왜 나누는 게 나은가

**① 이 프로젝트의 최대 리스크는 "또 `admin.js`처럼 되는 것"입니다.**
5,743줄짜리 파일이 다시 생기지 않으려면 `CLAUDE.md` 의 3층 구조 규칙이 매번 지켜져야 합니다.
규칙 문서를 기준으로 일관되게 작업하는 쪽에 **기능 개발**을 맡깁니다.

**② 동후 님은 코드를 읽지 않으십니다. 그래서 "검증"이 진짜 병목입니다.**
지금은 제대로 됐는지 확인하는 방법이 배포 후 눈으로 보는 것뿐입니다.
Antigravity는 브라우저를 직접 조작해 확인하고 그 과정을 남기므로, 이 부분이 크게 개선됩니다.
"로그인해서 출근 버튼 누르고 근무시간이 맞게 나오는지 확인해줘" 같은 지시가 가능합니다.

**③ Firebase 작업은 Antigravity가 붙어 있습니다.**
Firebase MCP가 기본 제공돼서 hosting 배포, 보안 규칙, 인덱스, Functions 로그를 직접 다룹니다.
지금 Gemini로 배포하시는 흐름의 자연스러운 연장입니다.
특히 **hosting을 사이트 2개로 나누는 초기 설정**은 손이 많이 가는데, 맡기기 좋은 일입니다.
